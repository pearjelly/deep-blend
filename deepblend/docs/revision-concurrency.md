# 修订与素材发布的写入协调

创建项目、提交补丁、直接提交事务和恢复修订共用项目写锁。编译期间锁仍然有效，直到修订、
当前指针和幂等记录写完才释放。同一项目的第二个写请求返回 `REVISION_CONFLICT`；调用方应
等当前写入结束，重新读取场景后再提交。相同幂等键在完成后的重试仍返回原来的结果。
不同项目可以并行编译。

恢复操作可传 `expectedCurrentRevision`：在取得项目写锁后，核对当前指针是否仍是调用方
看到的版本；不匹配返回 `REVISION_CONFLICT`，指针与历史均不变。工作台恢复和视觉循环的
自动回退携带此条件。已有 API 调用可以省略以保留原行为，但多人或多页面工作流应提供。
恢复只移动当前指针，不生成新版本，也不删除后来版本。

素材下载和流式复制不持有项目锁。复制完成后，内容发布以及素材清单的别名、版本历史更新
在同一把项目锁内同步完成。其他进程正在写项目时，导入在发布内容前返回 `REVISION_CONFLICT`，
并删除本次 `.incoming-*` 文件和远程下载暂存目录。等写者结束后，可以用相同导入参数重试。
同名别名的新内容替换当前别名，历次版本及其内容均保留；不同别名的更新不会互相丢失。
复制开始时读到的修订可能过期，因此成功结果中的当前修订在取得写锁后重新读取。

每次事务使用带 UUID 的独立 staging 目录。发布前再次检查写锁所有权和完整的项目记录；
编译期间发生的指针或历史变化会拒绝候选修订。失败只清理本次事务自己的 staging。

## 跨进程范围

写锁通过本地文件系统的原子目录创建实现。多个 Node/DSH 进程只要使用相同的真实工作区路径，
并通过上述入口修改修订，就会遵守同一把锁。锁位于工作区的 `.revision-writers/`，按项目
真实路径摘要命名，记录主机名、PID、唯一 token 和创建时间。

锁不会按时间过期，避免慢编译被另一进程接管。只有同一主机上的已记录 PID 明确不存在时，
下一写者才会恢复它并清理未发布的 staging。恢复操作有单独的原子 guard，防止两个恢复者
同时删除和替换写锁。

以下情形保守拒绝，不会自动删除锁：

- 所有者记录缺失或损坏。
- 主机名不一致、进程检查返回权限错误，或者 PID 仍然存活。
- 恢复过程被中断，留下 `.recovery` guard。

错误结果包含具体 `lockPath`。遇到这些情况，应先停止所有共享该工作区的写入进程并检查
锁记录；确认没有活跃写者后，仅清理错误指向的残留锁或恢复 guard，再重试。

这不是多主机分布式锁，不承诺网络文件系统的锁语义。直接改写磁盘或调用低层 `writeRecord`
会绕过协调；发布前的记录检查可发现部分外部修改，但不构成对任意外部写入的原子事务。
渲染任务和项目列表缓存各自的并发策略不由这把项目写锁替代。素材内容与清单不是跨文件的
原子事务：内容发布后、清单落盘前被杀可能留下未引用的内容文件；重试会复用这些字节，
不会覆盖已有内容，也不会把尚未成功写入的来源记录描述为已完成。

## 验证

`deepblend/tests/contract/revision-concurrency.test.mjs` 使用真实 Host、ProjectStore、事务代码和
可控异步编译替身，验证补丁竞争、恢复与清扫竞争、失败后重试、发布前记录变化以及不同项目并行。
检查成功结果对应的 SceneSpec、检查点内容和 revision manifest 摘要一致。

跨进程用例启动两个真实 Node Host 进程，验证第二写者和恢复操作被拒绝；另将持锁进程
`SIGKILL` 后启动新进程，验证死写者恢复和未发布 staging 清理。这里没有启动真实 Blender；
编译器替身的目的是准确控制竞争窗口，不能代替 Blender 编译与渲染验收。

素材用例使用两个真实 Node 进程，分别验证不同别名以及同一别名的不同内容。竞争者被拒后
清理自己的临时文件，重试成功后两个版本的摘要和字节都在，当前别名指向最后发布的版本。
另使用真实本地 HTTP 服务器验证慢下载期间修订仍可提交；下载完成时遇到忙锁会清理两份
临时文件，之后可以重新导入。
