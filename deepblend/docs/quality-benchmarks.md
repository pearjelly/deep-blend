# 可重建作品质量基准

这套基准用三个原创产品场景检查 DeepBlend 的造型、材质、装配和摄影能力。输入是公开 SceneSpec，输出包括真实 Blender 检查点、多视角图片、几何证据和动画。它把“能运行”与“作品好看”分开记录，方便复查具体改进。

## 三个案例

| 案例 ID | 设计与主要检查内容 | 固定设计要求 |
| --- | --- | --- |
| `metal-lamp` | 香槟金属桌灯：连续灯罩、实体卷边、珐琅内衬、曲线弯臂、关节与贴地电线；检查金属高光和曲面连续性 | [brief](../benchmarks/metal-lamp/brief.md) |
| `glass-ceramic` | 透明香氛空瓶与青釉托盘：厚壁、瓶肩、瓶口、独立套环和瓶盖、陶瓷脚圈；检查透射与实际接触 | [brief](../benchmarks/glass-ceramic/brief.md) |
| `modular-speaker` | 桌面音箱：有空腔的圆角柜体、真实编织格栅、滚花旋钮、散热开口、螺钉与接口；检查细节层级和完整装配 | [brief](../benchmarks/modular-speaker/brief.md) |

每个案例目录包含：

- `scene-spec.json`：成品候选的公开输入。
- `baseline-scene-spec.json`：主动简化几何和材质的消融对照。
- `brief.md`：固定尺寸、摄影目标、具体验收条件和能力限制。
- `geometry-checks.json`：要求封闭的实体、世界空间尺寸范围，以及适用时的体积范围。
- `build.mjs`：可选的确定性数值生成脚本，只生成公开文档并检查 contracts；不使用自定义 bpy 创建隐藏几何。

三个案例均不依赖外部模型、纹理、HDRI 或字体。它们验证的是公开场景表达与执行能力，不代表任意自然语言提示都能自动生成同等质量，也不属于工业制造、光学或声学认证。

## 对照能说明什么

**baseline 是现在构造的简化消融，不是历史版本输出。** 不应把两张图标成“升级前/升级后”或用作旧版本质量的证据。

候选与对照保持相机、镜头、世界环境、灯光、曝光、shots、动画及渲染配置相同；共同保留的实体也保持相同变换。各 brief 明确说明删除或简化了哪些零件和表面。灰模另把非 `environment` 实体统一赋为中性灰材质，帮助查看轮廓和结构。

当前对照同时改变几何和材质，所以只能评价这些变化的组合效果。若需要区分倒角、细分、纹理或灯光的独立贡献，应增加一次只改变一个因素的对照；不能从这套结果推导竞品排名。

## 固定预算

预算的机器可读来源为 [manifest.json](../benchmarks/manifest.json)。每个案例上限为 150,000 个编译后多边形，包含场景中的隐藏布尔操作数。所有案例单位为米，时间为帧 1–48、24 fps。

| 档位 | 静帧规格 | 默认静帧内容 | 动画 | 单案例时间预算 |
| --- | --- | --- | --- | --- |
| `draft` | Cycles，384×288，16 samples | 候选 `hero`、`detail`、`reverse`，共 3 张 | 无视频 | 300 秒 |
| `review` | Cycles，768×576，64 samples | 候选 5 张、对照 3 张、灰模 2 张，共 10 张 | 候选第 24、48 帧作为静帧 | 900 秒 |
| `final` | Cycles，1024×768，128 samples | 同 review，共 10 张 | 48 帧，384×288，24 samples，24 fps，编码为 MP4 | 1,800 秒 |

所有档位使用 AgX。每个案例的 preview 与 final 使用一致的色彩管理和曝光；不能为对照单独调曝光。`draft` 仅用于检查构图、接触、穿插和严重曝光问题，细小材质与轮廓应以完整规格图判断。final 的视频使用独立的较低分辨率预算，不能当作 1024×768 的成品动画。

默认静帧为：

- 候选：`hero@1`、`detail@1`、`reverse@1`、`hero@24`、`hero@48`。
- 对照：`hero@1`、`detail@1`、`reverse@1`。
- 灰模：`hero@1`、`detail@1`。

案例可在 manifest 中声明 `motionCameraId`，将候选第 24、48 帧及整段视频切换到同一个动作机位。当前音箱使用 `motion-detail`，让 0.7 mm 的按键行程在低清视频中仍可辨；主图、细节和背面三视角保持独立。

时间预算按案例计算，并不等同于整次运行的时限。三个案例顺序执行；实际耗时还受硬件、编译、几何检查和编码影响，应读取每次运行的记录。

## 运行前准备

在仓库根目录运行命令。需要：

1. Node.js ≥22，以及已经可解析的仓库/DSH 工作区依赖。首次开发环境配置见 [安装说明](install.md)；需要建立独立开发环境时，由操作者显式运行 `npm run dev:setup`。
2. 与 [blender-release.json](../tools/blender-release.json) 固定版本一致的 Blender。当前固定为 5.2.1。默认路径是 `.tools/Blender.app/Contents/MacOS/Blender`；其他安装位置通过 `DEEPBLEND_BLENDER_PATH` 指定。
3. final 视频编码需要 PATH 中的 `ffmpeg` 与 `ffprobe`。`draft` 和 `review` 静帧流程不需要视频编码器。

基准命令不自动安装或升级这些依赖，也不自动下载素材。`--check` 不启动 Blender，但工具的 Node 工作区依赖仍须能解析。仅通过 `--check` 不证明 Blender、Cycles 或编码器可用。

## CLI

先检查全部公开输入与固定预算：

```sh
npm run quality:check
```

`npm run quality:render -- <参数>` 等价于下面示例的直接 Node 命令，默认使用 `review` 档位。两个入口的检查与输出规则相同。

查看单个案例的低清三视角：

```sh
node deepblend/tools/quality-benchmark.mjs \
  --case glass-ceramic --tier draft \
  --output .deepblend/quality/benchmarks/glass-draft-v1
```

生成三个案例的完整 review 对照：

```sh
node deepblend/tools/quality-benchmark.mjs \
  --case all --tier review \
  --output .deepblend/quality/benchmarks/review-v1
```

生成完整 final 静帧、对照、灰模与动画：

```sh
node deepblend/tools/quality-benchmark.mjs \
  --case all --tier final \
  --output .deepblend/quality/benchmarks/final-v1
```

调试时可以只渲染指定画面：

```sh
node deepblend/tools/quality-benchmark.mjs \
  --case metal-lamp --tier review --views hero,detail \
  --output .deepblend/quality/benchmarks/lamp-detail-v1
```

`--views` 接受 `hero,detail,reverse,motion-mid,motion-end` 中的 ID，应用于本次各变体，并关闭整段视频生成。它属于局部运行，即使指定 `--tier final`，也不能当作完整 final 结果。

成功渲染后自动进行独立产物审计；也可以重新核验已有完整目录：

```sh
npm run quality:verify -- --output .deepblend/quality/benchmarks/final-v1
```

审计只写 `artifact-verification.json`，保留原始运行记录。final 必须同时通过渲染和产物审计；完整图片帧被逐一解码比较，PNG 的帧号/日期元数据不算运动证据。静帧曝光由绑定摘要的真实检查点读回核验，视频曝光由渲染回执核验。每个静帧的实际机位、帧号、尺寸和字节数还须与渲染回执及保留的案例输入相符。命令返回失败时，应查看报告中的具体错误。

默认档位是 `review`，默认运行全部案例；省略 `--output` 时创建独立的新目录。已有 `run.json` 的目录会被拒绝，以保留前次证据。每轮调整使用新目录，例如 `v1`、`v2`；不要覆盖前一轮图片后仍沿用旧结果摘要。

重新生成 JSON 时，执行对应目录的 `build.mjs`，然后重新运行 `--check`。冻结案例与执行代码后再进行正式批次，保证同一批结果使用同一份输入和实现。新运行从输出目录的 `source-snapshot/` 执行 Blender Python 和几何检查脚本，并在 `runtimeSources` 记录路径，避免渲染期间工作区编辑改变后续阶段的实现。

## 证据在哪里

结果保存在指定输出目录，均为本地文件：

| 文件 | 用途 |
| --- | --- |
| `index.html` | 并排/滑动比较、细节、背面、灰模、动画与 brief；用浏览器打开审阅 |
| `run.json` | 本次档位、选择的视图、源码版本及文件 SHA-256、设备与版本信息、各案例状态 |
| `source-snapshot/` | `run.json` 列出的执行代码、案例与配置文件副本，用来核对本次实现 |
| `<case>/result.json` | 输入摘要、技术状态、美术待审状态、每变体耗时、面数、图片规格及哈希 |
| `<case>/<variant>/scene-spec.json` | 实际用于编译的已解析 SceneSpec |
| `<case>/<variant>/scene.blend` | 真实编译后的检查点，可供独立打开复核 |
| `<case>/<variant>/compile.json`、`views.json` | 编译与视图渲染回执，包括实际渲染配置 |
| `<case>/<variant>/verification-geometry.json` | 绑定检查点摘要的独立读回：几何、全部 48 帧姿态、实际曝光与色彩管理 |
| `artifact-verification.json` | 解码像素、完整帧序列、来源绑定、实际预算与视频参数的独立审计 |
| `<case>/candidate/geometry.json` | 从真实检查点读取的网格与时间姿态证据 |
| `<case>/motion/` | final 的逐帧 PNG 和 MP4；局部运行不生成此目录 |

源码快照按 `run.json` 的文件清单保存，不能当作完整依赖、Blender 或操作系统环境的备份。需要完整重现时，应同时保存对应提交及未提交改动、依赖版本配置、输入 JSON 和结果目录。相同输入在不同 GPU/驱动/渲染器版本下不承诺 PNG 字节完全相同；哈希用于识别某次证据，不能替代视觉比较。图像是否发生可见变化应比较解码后的像素，不能只看包含帧号和耗时元数据的 PNG 文件哈希。

## 技术验证与美术判断

技术验证检查公开契约、编译、面数、图片尺寸、非空画面以及几何约束。独立检查脚本打开已经编译的 `.blend`，读取求值网格的边界边、非流形边、带符号体积、世界包围盒、UV 与材质库存；不是把 `geometry-checks.json` 的声明值当成测量结果。玻璃案例另外用体积区间检查内腔没有被填实。

几何报告还读取实际时间姿态，以发现“声明了动画却没有生效”。完整 final 保留所有动画帧，并检查编码帧数、分辨率和帧率。相同起止姿态是合法循环；仅凭首尾相同不能判定没有动画。具体取样与检查数据可在 `geometry.json`、逐帧信息和视频中复核。

这些检查有明确边界：封闭且正体积不证明零件没有相互穿插，几何尺寸通过不证明高光连续，图片发生变化也不证明动作可读。应按各 brief 独立审阅：

1. 造型轮廓、厚度与空腔是否成立。
2. 金属、透明玻璃、陶瓷与织物是否有明确区别。
3. 接缝、装配、贴地与接触阴影是否可信。
4. 构图、曝光与细节镜头是否支持判断。
5. 动画是否保持装配，并能看清预定动作。

`technical-pass` 只说明本次技术检查通过；完整运行的汇总状态仍带 `review-required`。美术结论需要审阅者、对应图片和具体理由。结果没有自动给作品打“优秀”或“商业可交付”的标签。

## 成本口径与结果发布

记录中的 `modelCalls: 0` 表示这次确定性重建/渲染流程没有发起模型调用，不统计前期编写设计和 SceneSpec 的模型使用。**0 次模型调用不等于 0 渲染成本。** Blender 编译、Cycles CPU/GPU 时间、视频编码、存储和审阅仍有成本。比较成本时应同时注明硬件、档位、图像/帧数和实际耗时。

正式结果数据在统一批次完成后填写；不把各作者不同轮次的 draft 混成同一次 final。发布时至少附上运行目录或证据包、源代码/输入标识、实际规格、技术状态与独立美术结论，并明确消融对照的含义。

## 2026-10-03 本机结果

本地审阅入口：`.deepblend/quality/benchmarks/product-gallery/index.html`。它是三个已核验批次的索引，逐案例链接原始记录：台灯使用 `final-metal-lamp-r13-v1`，玻璃陶瓷使用 `final-products-v1`，音箱使用 `final-modular-speaker-r13-v3`。原批次与旧画廊索引保留，不能把汇总索引当作一次共同执行的原始日志。日期按本地 Asia/Shanghai 记录，原始日志使用 UTC。

| 当前案例 | 全场景面数，含隐藏操作数 | 完整案例耗时 | 静帧 / 动画 |
|---|---:|---:|---|
| 金属台灯 r13-v1 | 50,875 | 312.3 秒 | 10 张 1024×768；48 帧 384×288、24 fps |
| 玻璃陶瓷 v1 | 35,617 | 385.3 秒 | 同上 |
| 多部件音箱 r13-v3 | 38,825 | 309.4 秒 | 同上 |

设备为 Apple M5、10 逻辑核、16 GiB 内存、macOS arm64；Node 25.9.0，Blender 5.2.1 LTS。期间也运行了契约检查，以上是本次实际耗时，不用于不同机器的性能排名。模型调用计数仅覆盖重建命令，创作与审阅未包含其中。

三个原始批次都用当前审计工具重新通过独立产物审计：每个案例的 48 张动画 PNG 被真实解码；音箱首尾回位，第 2–47 帧与首帧像素不同。每段 MP4 实际为 48 帧、384×288、24 fps。三案例的主要实体共 26 项封闭检查、38 项尺寸检查通过；玻璃壳实测体积 124.353 mL，符合解析截面给定的体积区间。

首批渲染工具尚未排除 PNG 帧号元数据对运动摘要的影响，也未在静帧回执中记录曝光。此问题在审阅中发现后修正：首批完整保留；额外只读重开 9 个检查点，写入带检查点与检查脚本摘要的 `verification-geometry.json`；最终独立审计对像素、实际曝光及来源重新核验。新台灯、音箱运行自动产出这些证据，实际执行保留的 Python 快照；没有用当前文件覆盖旧快照。音箱 r13-v2 在执行期间遇到工作区实现变化，另留来源说明，最终选用重新冻结执行的 r13-v3。

### 图像审阅记录与余项

以下是本次代理对实际图片的观察，不替代外部用户的美术验收：

- 台灯：实体唇边、内衬、弯臂和关节可辨；消融特写暴露低细分轮廓，候选连续。旋压灯罩、底座和关节改用明确径向切线的各向异性金属，支架保留均匀细抛光；专门材质测试验证旋转方向会改变真实高光。背面机位抬高并调整目标，保留线缆边距并移除背景边缘。成品仍偏柔和缎面，微观拉丝凹槽尚未通过贴图表达，不能把各向异性参数本身当成细密纹理。
- 玻璃陶瓷：可观察透明厚壁、实体瓶口、空腔、独立瓶盖和釉面托盘；灰模确认内腔不是靠透明材质伪造。设计明确为空瓶，不模拟液体或标签。
- 音箱：真实编织经纬、旋钮滚花、刻度、圆角、接缝、后板开口和螺钉可读。平面/加权法线、漫反射和灰模对照均保留原背角暗带，测得该处法线背向三盏原有灯的中心方向；增加 1 W 后角补光后改善，候选与消融共用灯光。动作视频改用 85 mm 局部机位，0.7 mm 行程在 384 像素宽画面中约占 6.85 像素。消融保留后板装配槽的必要布尔开口，修正旧对照的共面黑斑；其余几何与材质简化仍保留。

汇总画廊经过真实浏览器复核：30 张图片全部加载，3 段视频各 2 秒且无媒体错误；主图滑块改变实际裁剪边界，所有相对证据链接存在。这些观察写入本地 `ui-verification.json`，不等同于外部用户美术通过。

这些案例建立了可重建的质量下限和检查入口。自然语言创作稳定性、自动选择建模方案，以及非维护者能否独立达到这些结果，仍属于后续验收。
