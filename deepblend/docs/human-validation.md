# 真人创作、内容投稿与独立采用验收

这份指南用于组织实际试用，查清作品为什么仍显得粗糙，以及外部用户和作者能否独立完成工作。复制下面的空白记录到参与者自己的目录；空白表、维护者演示和自动测试都不计入真人验收结果。

验收人数与整体状态以 [改进路线](improvement-plan.md) 为准。这里说明如何执行与记录，不提前宣布任何参与者通过。组织者先与参与者约定任务、时间和实际费用上限；由参与者决定是否分享作品与记录。公开记录可使用稳定化名，私下核对其参与角色，不收集账号密钥。

## 先确定正在试用哪份产品

1. 按 [安装说明](install.md) 准备环境，记录实际安装路线、提交或包版本、操作系统、DSH、Blender 版本/构建和渲染设备。
2. 试用未发布改动时，使用组织者提供的精确源码提交或对应包文件。相同版本号不足以区分未发布源码与 registry 中的旧包；包文件同时记录实际 SHA-256。
3. 使用自己的工作目录与项目。安装时记录实际 profile 和配置改动；需要维护者操作时，写下原因和具体操作。
4. 打开工作台，创建项目并查看实际预览。失败时保留诊断、错误码、复现步骤和已完成的产物，按 [恢复指南](recovery.md) 处理。

环境准备、使用过程、渲染等待和维护者介入分别计时。费用记录实际金额和币种；未接入在线模型或无法取得账单时填写“未使用”或“未知及原因”，不能填成零费用。

## A. 非维护者用自己的素材完成作品

复制 [创作记录](validation-templates/creation-session.md)。参与者先写目标：产品或场景、尺寸/比例、部件、表面、摄影、参考和交付规格。记录自己提供的素材及使用许可，可选自包含 GLB、图片纹理或环境图；受支持格式与限制见 [素材指南](assets.md)。

按实际任务选起点：已有配方、自己的模型导入，或通过 Agent 创建场景。模板只是起点，完成作品必须包含参与者自己的素材与创作决定。建议让不同参与者覆盖不同路线，避免所有人只重复点击同一模板。

| 步骤 | 参与者实际完成的事情 | 保留的证据 |
| --- | --- | --- |
| 目标与素材 | 保存文字目标、适用的参考图和自己的素材；确认主要评审对象 | 素材来源/许可、原文件摘要、目标与对应修订 |
| 结构 | 核对比例、厚度、接缝和部件，完成至少一项与目标有关的尺寸或形状修改 | 修改前后修订、具体操作、主视角和特写灰模 |
| 表面与摄影 | 按目标处理局部材质、纹理尺度、高光、背景与接触阴影 | 材质图、实际相机/帧、曝光、引擎与采样记录 |
| 保存与恢复 | 刷新后继续工作；确有需要时恢复旧版，再确认旧作品仍可查看 | 实际版本记录、失败与恢复结果；未执行的步骤明确注明 |
| 交付 | 按原任务完成可打开的 PNG 或视频，核对尺寸；动画另外核对时长、帧率和动作 | 实际文件、渲染/导出回执、摘要及参与者结论 |

使用 [创作流程](usage.md)、[建模指南](modeling.md) 和 [固定视角检查](inspection.md)。无法完成一步时，记录卡点及当时画面，保留部分作品。维护者替参与者完成作品不能被统计为独立完成；口头建议、修改输入、配置环境和直接代做分别记录。

### 专门判断“粗糙”的四个维度

参与者先独立写结论，再与维护者讨论。每项使用“通过 / 需改善 / 无法判断”，指出实际图片、相机、帧、局部区域及理由。技术分单独记录，不能覆盖这份判断。

| 维度 | 具体观察 | 用什么画面判断 |
| --- | --- | --- |
| 几何 | 轮廓是否有不合目标的折线；倒角和厚度是否合理；根部/装配接缝有无突兀扩张、夹痕或穿插 | 主视角、侧/背面、连接特写和灰模；封闭性另查实际网格报告 |
| 材质 | 金属、陶瓷、玻璃等是否可辨；粗糙度和纹理尺度是否符合目标；部件边界是否正确 | 相同摄影条件下的材质图与近景；透明物体需能看清内外表面 |
| 灯光 | 光线是否解释形体；高光有无干扰性光斑；暗部、接触阴影和背景是否可读 | 完整画面与关键局部，保留实际曝光/色彩配置 |
| 目标吻合 | 比例、部件、表面和交付是否符合事先保存的目标及适用参考 | 目标、明确参考 ID 和对应实图；缺少证据时不能声称参考吻合 |

跨版本比较先确认相机、帧、灯光、环境、资产、曝光和渲染设置。一次只改变一个因素，才可归因到该因素；同时改造型与材质时只能判断组合效果。灰模会改变光线传播，不用于证明相同材质光照效果。详见 [作品评审](artistic-review.md) 与 [质量基准](quality-benchmarks.md)。

## B. 外部作者投稿，另一名用户实际复用

复制 [作者投稿与复用记录](validation-templates/author-submission.md)。作者自行确定作品和构造路线，遵守 [配方指南](recipes.md) 的当前能力范围，准备 `recipe.json`、`scene-spec.json`、`preview.png`、`LICENSE`。不要把维护者改好的包当成作者独立产出。

1. 在仓库外自己的 Node 项目安装对应 contracts 包，运行 [作者示例](../examples/content-author/README.md) 的 `validate-recipe.mjs`。保留默认报告、实际 SDK 版本、包身份及选定参数报告。
2. 经实际 Blender 构造并生成默认预览，保留输入、构建、相机/帧、引擎、尺寸、采样、耗时和原始图片。选定值或参数范围的画面声明必须有对应真实渲染，有限数据验证不证明所有组合的画面质量。
3. 按 A 的四维标准审阅主图、相关细节和灰模；核对预览确实来自提交的输入。声明原创内容、复用内容及再分发依据；许可文本存在不证明权利。
4. 按 [PR 模板](../../.github/PULL_REQUEST_TEMPLATE.md) 准备投稿。在本地验证与审阅完成后，由实际作者自行决定是否提交 PR。
5. 另一名用户在自己的安装环境复用同一个 `id/version/digest`。由环境维护者配置本地 `recipeDirectories`，使用者重新列出配方，选择参数并实际创建、渲染，记录来源锁、实际值、输入及图片摘要。配置方式见配方指南。

作者本人再次创建自己的包只算自测。复用者需与作者不同，记录是否为项目维护者、受到哪些帮助，以及实际失败或成功。配方移走或升级后的来源保留、旧版本不被改写，也应由实际记录证明，不能只抄机制说明。

## C. 独立公开接口使用方

复制 [接口采用记录](validation-templates/interface-adoption.md)。记录实际使用方、独立代码来源、对应公共包版本/摘要、公开入口、实际执行和维护者介入。仓库内示例、改名副本和维护者自行编写的消费者不计为独立采用。

- **内容工具使用方**：按 [公共 API](public-api.md) 在仓库外使用 `/sdk` 或版本化 Schema，处理自己的输入，实际校验、编译、应用补丁或实例化配方；保留一次实际错误处理。声明自己覆盖的操作，不能从一次成功推导全部契约兼容。
- **运行时使用方**：独立实现公开 `BlenderRuntime` 边界，按公共 API 的行为要求提供实现自己的检查，记录实际输入/输出、真实执行、失败、取消、生命周期与版本兼容。当前维护的 SDK 消费者测试不提供可直接接纳任意第三方运行时的通用验收入口；仅通过类型检查不足以验收运行时。脚本化返回值可检查 Host 接线，但不能作为真实渲染执行证明。

整体路线要求的使用方数量与范围另行核对。内容 SDK 采用不自动证明独立运行时已存在；参与者角色可重叠，但不能借重复记录把同一个使用方算成多个。

## 汇总、反馈与完成判据

组织者用记录 ID 关联原始作品、来源和审阅。把问题分为任务阻断、质量不达目标、操作困惑和成本问题；按影响人数、严重程度、复现证据及修复成本排序。修复后请原参与者用自己的任务复查，不用维护者演示替代。

对每份记录分别确认：实际参与身份与角色、安装身份、自己的输入、真实执行、四维作品结论、耗时/费用、介入和可查看产物。只有具备这些证据，才能评价“独立完成”或“作品达标”。未发生、缺证据、受支持范围外和无法判断均单独保留，不能归入通过。

整体验收还需按改进路线核对真实人数、独立作者、另一人复用和公开接口使用方。准备好指南或填完表格只说明材料齐备；实际结果和仍未解决的问题写入 [验收记录](milestone-status.md)，产品说明引用对应证据。
