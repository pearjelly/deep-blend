## 产品定位与判断依据

DeepBlend 的核心目标是在 DSH 中让用户用一句任务描述和少量操作，完成复杂、高质量且可继续编辑的 Blender 建模。当前从配方或自己的模型开始，优先改善尺寸、造型、装配联动和几何质量，使用实际文件与真实预览判断结果，保留可回退版本；摄影、PNG 和 MP4 服务于完整建模交付。

核心用户是需要产品模型和完整交付的小团队与独立创作者。首要价值是少量操作得到可用、可继续修改的模型。功能优先级按真实任务收益、覆盖范围、证据强度、实现成本和兼容风险确定；现有配方案例不等于任意自然语言建模已完成。

## 首轮两周安排（原始排序）

日期是工作目标；每次恢复时根据已发布版本、失败记录和反馈重排。下列版本功能需要实现与验证后才进入正式发布说明，不提前声称完成。

| 日期 | 用户收益与工作切片 | 验收依据 |
| --- | --- | --- |
| 10-10 | 环境自检：一次列出依赖问题、修复动作，区分图片创作与可选视频编码 | 缺失/版本不符/超时/完整环境、真实执行、npm pack 入口 |
| 10-11 | 首次成功路径：清晰显示创建与预览状态、失败后可继续 | 独立 profile 从安装到首张 PNG；记录实际耗时与卡点 |
| 10-12 | 配方选择：作品用途、输入参数、实际预览与预计输出范围 | 公开配方输入、预览来源和创建结果对应 |
| 10-13 | 保存与对照：确认本次改动保存在哪个版本，可继续调整 | 编辑、保存、冲突、对照和回退的真实浏览器检查 |
| 10-14 | 摄影效率：把重复灯光/构图操作做成可复用选择 | 固定模型前后图；保存与重建一致，历史版本可读 |
| 10-15 | 动画起步：让用户明确选择并预览实际运动 | 实际首中末帧与编码；增加帧数不能冒充动画 |
| 10-16 | 导出效率：常用尺寸/格式、当前版本与输出路径可见 | PNG/MP4 设置、真实尺寸/帧数和 manifest 对应 |
| 10-17 | 失败恢复：可读的原因和可执行的下一步 | 中断、取消、损坏帧和编码失败的实际恢复 |
| 10-18 | 自有模型路径：导入保真、素材错误与预算反馈 | GLB/OBJ 真实素材；材质/UV/变换与源字节核对 |
| 10-19 | 图文教程：一项真实任务从新环境做到交付 | 教程逐步执行，截图和输出来源可复现 |
| 10-20 | 质量短板：从作品对照与已有问题挑最影响使用的一项 | 固定条件的材质/灰模前后图与独立技术检查 |
| 10-21 | 内容作者路径：创建配方、检查、投稿材料与复用 | 仓库外作者示例与公开 SDK；外部参与另记 |
| 10-22 | 安装与升级体验：保留项目、配置与其他插件 | 隔离 profile 的升级、共存、卸载与重装 |
| 10-23 | 汇总实际反馈，重新排序第二轮；发布一个已验证改进 | 真实反馈与产物证据，明确未完成项 |

每天围绕一项可说明的改善发布 patch；新增稳定能力进入 minor。较大能力可以跨日实施，期间发布其他独立验证的有价值切片。没有通过验证的改动继续留在候选，不能靠空升版本满足日更。

## 如何衡量是否有用

| 指标 | 观察方法与目标 |
| --- | --- |
| 首次创作成功 | 从干净安装到 PNG 输出的成功/失败、耗时、人工介入；先建立基线，再设改进幅度 |
| 完整任务成本 | 固定配方与硬件的创建、预览、调整、交付耗时，记录模型调用成本；不同条件不混算 |
| 修改效率 | 完成相同目标的操作次数、等待与返工次数；保留前后作品与场景版本 |
| 交付可靠性 | 真实任务中的失败、取消、恢复和完整交付；确认 PNG/MP4 字节、帧数与来源 |
| 作品质量 | 同输入/机位/预算的实图对照，分别判断几何、材质、灯光与目标吻合 |
| 实际采用 | 收到授权的非维护者体验、配方投稿/复用、重复使用和问题反馈；不虚构用户与访谈 |

真人验证沿用[既有指南](human-validation.md)。没有真实参与时标记未测；未经授权不向他人发消息。

## 每日执行与发布

每四小时在当前聊天恢复工作。以北京时间自然日为发布统计边界，目标每天至少一个稳定版本；日间完成主要实现，预留完整验收与发布时间。只有进展、完成、失败或需要用户提供信息时通知。

1. 检查工作树、版本源、近期提交、公开 Release/npm 和社区状态，接续已有候选，保留用户修改。
2. 选定用户任务与验收条件；先复现问题或测量当前行为，实施一个可独立交付的切片。
3. 完成契约检查；涉及 runtime、渲染或 UI 时执行仓库要求的连续完整验收。核对该提交实际 GitHub CI；截图、真实输出和模型验证按变更范围更新。
4. 只通过 `deepblend/version.json` 升版并同步八个清单。写清收益、兼容范围、验证与限制。
5. 按 [CONTRIBUTING §5](../../CONTRIBUTING.md#5-发一个版本四步是一次动作)，在干净、已推送的确切提交上构建，创建对应 tag 与 GitHub Release，附 bundle、校验和及原生验证材料。
6. 七个 npm 包按依赖顺序发布到公共 registry；逐包确认公开可读，bundle 在依赖可读后发布。已发布版本不可覆盖，部分成功从实际渠道状态恢复。
7. 从源码、npm、Release 三条路线在新 profile 安装读回，核对版本、工作台与预设。发布命令返回成功不足以表示完成。
8. 社区信息只从 `listing-entry.yml` 投影，核对社区最新规则，更新自有条目；已有未合并提交优先续用。区别记录“无需条目改动”“已提交”“已合并”和“线上已刷新”。上游审核由社区决定。
9. 更新[每日发布记录](daily-releases.md)，链接提交、验证证据、Release、npm 与社区状态，列明当天发布目标是否实现。

网络、权限、凭据或验收失败时，保留候选、原始失败和具体下一步，继续独立可做的工作。当天未完成的正式发布必须如实记为未达标；不能把本地 tag、计划、自动任务或社区 PR 当作正式发布。
